# Internationalisation Rules

## Always use t()

Every user-facing string goes through the translation function. Never hardcode English strings in
JSX or server responses.

```tsx
// ✓
<Typography>{t("invoices.status.paid")}</Typography>

// ✗ - hardcoded string
<Typography>Paid</Typography>
```

## Server vs. client usage

- Server components and server actions: import `t` from `@/lib/i18n/server`.
- Client components: use the `useTranslation` hook from `@/lib/i18n`.
- Shared non-React modules that can be imported by client code, such as client-used Zod schemas:
  import the i18next singleton from `@/lib/i18n/i18n` and call `i18n.t(...)` directly.
- Do not import `@/lib/i18n/server` from client-safe modules.

```ts
// ✓ - server component
import { t } from "@/lib/i18n/server"

// ✓ - client component
import { useTranslation } from "@/lib/i18n"

const { t } = useTranslation()

// ✓ - client-safe schema/shared module
import i18n from "@/lib/i18n/i18n"

i18n.t("settings.profile.validation.nameRequired")
```

## Adding a key

Adding a new translation key requires two steps, both in the same commit:

1. Add the key to the `Translations` type in `lib/i18n/types.ts`.
2. Add the English value to `lib/i18n/locales/en.tsx`.

The compiler rejects any `t("...")` call whose key does not exist in `Translations`. Never add a key
to `en.tsx` without adding it to `Translations` first - the locale object must satisfy the type.

## Key structure

Keys use dot notation: `<feature>.<section>.<name>`. Keep nesting shallow - three levels max.

```ts
// ✓
"invoices.actions.markAsPaid"
"settings.email.testSend"
"common.actions.save"

// ✗ - too deep, too vague
"invoices.list.table.row.actions.buttons.markAsPaid"
"label1"
```

`common.*` is for strings reused across features (save, cancel, delete, confirm, etc.). `errors.*`
is for generic error messages. Feature-specific strings live under the feature key.

## ICU parameters

Use ICU MessageFormat for dynamic values - never string interpolation or concatenation.

```ts
// ✓ - ICU parameter
t("invoices.dueIn", { days: 3 })
// en.tsx: "Due in {days, plural, one {# day} other {# days}}"

// ✗ - concatenation breaks translation
"Due in " + days + " days"
t("invoices.dueIn") + days
```

## Error messages

Error messages returned from server actions are translated on the server using `t()` from
`@/lib/i18n/server` before being returned. The `errors.*` namespace holds shared keys for common
failures. The client displays the already-translated string directly - no `t()` call on the error
value at the call site.

```ts
// ✓ - server action translates before returning
import { t } from "@/lib/i18n/server"

return { error: t("errors.somethingWentWrong") }
return { error: t("errors.unauthorized") }
return { error: t("invoices.errors.notFound") }

// ✗ - hardcoded English string bypasses i18n
return { error: "Something went wrong" }
return { error: "Invoice not found" }
```

Zod validation messages in `schemas.ts` are also translated at definition time. If the schema can be
imported by client code, use the i18next singleton directly with `i18n.t(...)`. Never use Zod's
default English messages and never import `@/lib/i18n/server` into a client-safe schema.

```ts
// ✓ - client-safe schema uses i18n.t() for validation messages
import i18n from "@/lib/i18n/i18n"

const createInvoiceSchema = z.object({
  number: z.string().min(1, i18n.t("invoices.validation.numberRequired"))
})

// ✗ - Zod default message is English-only
const createInvoiceSchema = z.object({
  number: z.string().min(1)
})

// ✗ - client-used schema depends on a server-only i18n entrypoint
import { t } from "@/lib/i18n/server"
```
